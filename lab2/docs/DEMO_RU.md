# Инструкция: запуск и демонстрация отказоустойчивости

## 1. Что у нас есть: 6 микросервисов, 14 контейнеров

Предметная область — интернет-магазин **ShopHub**.

| № | Микросервис | За что отвечает | Контейнер сервиса | Своя БД (отдельный контейнер) | Порт |
|---|---|---|---|---|---|
| 1 | **auth** | регистрация, вход, выдача JWT | `auth-service` | `auth-db` | 8001 |
| 2 | **user** | профили покупателей | `user-service` | `user-db` | 8002 |
| 3 | **product** | каталог товаров и склад | `product-service` | `product-db` | 8003 |
| 4 | **order** | заказы | `order-service` | `order-db` | 8004 |
| 5 | **payment** | оплата и возвраты | `payment-service` | `payment-db` | 8005 |
| 6 | **notification** | уведомления пользователям | `notification-service` | `notification-db` | 8006 |

Кроме них есть ещё 2 инфраструктурных контейнера. **Это не бизнес-микросервисы**, в задании они так и описаны:

| Контейнер | Зачем |
|---|---|
| `api-gateway` (порт 8080) | единая точка входа: маршрутизация, проверка токена, ограничение частоты запросов |
| `rabbitmq` (порты 5672, 15672) | брокер сообщений для асинхронных событий |

**Итого: 6 микросервисов, у каждого свой контейнер и своя база данных. Всего 6 + 6 + 2 = 14 контейнеров.**

Каждый микросервис — это изолированная пара «приложение + своя БД». Если что-то случится с одним из них
(упадёт процесс, упадёт его база, его обновят), остальные 5 пар этого даже не заметят.

## 2. Что нужно на компьютере

* Docker Desktop (запущенный).
* Windows PowerShell — для скрипта демонстрации.

## 3. Запуск

```powershell
cd lab2
docker compose up -d --build
```

Первая сборка занимает 1–3 минуты. Проверить, что всё поднялось:

```powershell
docker compose ps
```

Все 14 контейнеров должны быть в статусе `running (healthy)`.

Полезные адреса:

| Адрес | Что там |
|---|---|
| http://localhost:8080/docs | Swagger шлюза |
| http://localhost:8001/docs … http://localhost:8006/docs | Swagger каждого микросервиса |
| http://localhost:8080/ready | шлюз показывает, какие сервисы живы |
| http://localhost:15672 | панель RabbitMQ (логин `shop`, пароль `shop`) — видно очереди событий |

Администратор: `admin@example.com` / `Admin12345!`.

Остановить всё:

```powershell
docker compose down        # с сохранением данных
docker compose down -v     # и удалить базы данных
```

## 4. Демонстрация преподавателю

### Вариант А — автоматический скрипт (рекомендую)

Из папки `lab2`:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\failover-demo.ps1 -Scenario all -Pause
```

С ключом `-Pause` скрипт останавливается после каждого шага и ждёт Enter. За это время можно объяснить, что
происходит на экране.

Можно показывать сценарии по одному:

```powershell
# 1) сервис "выключили"
powershell -ExecutionPolicy Bypass -File scripts\failover-demo.ps1 -Scenario stop -Service payment-service -Pause
# 2) сервис "упал сам" (ошибка внутри, процесс умер) -> Docker сам его поднимает
powershell -ExecutionPolicy Bypass -File scripts\failover-demo.ps1 -Scenario crash -Service payment-service -Pause
# 3) упала база данных одного сервиса
powershell -ExecutionPolicy Bypass -File scripts\failover-demo.ps1 -Scenario database -Service payment-service -Pause
# 4) обновили один сервис -> перезапустился только он
powershell -ExecutionPolicy Bypass -File scripts\failover-demo.ps1 -Scenario update -Service payment-service -Pause
```

Вместо `payment-service` можно подставить любой из шести сервисов.

**Как читать вывод скрипта.**

Таблица состояния:

```
MICROSERVICE           SERVICE CONTAINER        OWN DATABASE         API
auth-service           running (healthy)        running (healthy)    UP
payment-service        exited                   running (healthy)    DOWN      <- упал только он
...
```

Проверка магазина — по одному реальному запросу к каждому микросервису через шлюз:

```
POST /api/auth/login        -> 200  OK
GET  /api/payments          -> 502  FAIL: payment-service is unavailable   <- только этот
GET  /api/notifications     -> 200  OK
```

Зелёное — работает, красное — то, что сломали. Красная строка всегда одна.

### Вариант Б — вручную, командами Docker

Если преподаватель хочет увидеть всё «руками». Откройте Docker Desktop (вкладка Containers) или выполните
`docker compose ps` в соседнем окне.

**Сценарий 1. Выключаем один сервис.**

```powershell
docker compose stop payment-service
```

Откройте http://localhost:8080/ready — там будет `"payments": false`, все остальные `true`.
Каталог http://localhost:8080/api/products открывается, магазин работает.

Включаем обратно:

```powershell
docker compose start payment-service
```

**Сценарий 2. Сервис «упал» — внутренняя ошибка, процесс завершился.**

```powershell
Invoke-RestMethod -Method Post http://localhost:8005/chaos/crash -Headers @{ "X-Internal-Token" = "dev-internal-token-change-me" }
docker compose ps payment-service
```

Процесс сервиса завершается с кодом 1, как при настоящей аварии. Через пару секунд Docker сам поднимает
контейнер: срабатывает `restart: unless-stopped`. Число перезапусков видно так:

```powershell
docker inspect -f "{{.RestartCount}}" payment-service
```

Остальные контейнеры при этом не перезапускались. Это видно по столбцу «Created / Status» в `docker compose ps`.

**Сценарий 3. Упала база данных одного сервиса.**

```powershell
docker compose stop payment-db
```

* `payment-service` жив (http://localhost:8005/health → 200), но не готов (http://localhost:8005/ready → 503, `"database": false`).
* Его API отвечает понятной ошибкой `503 database_error`. Никакого «stack trace», ничего не зависает.
* Остальные 5 сервисов и их 5 баз работают как обычно.
* Новый заказ при этом **принимается** со статусом `pending_payment`. Событие об оплате ждёт в RabbitMQ и
  повторяется каждые 5 секунд.

```powershell
docker compose start payment-db
```

Через несколько секунд сервис снова готов, и заказ сам становится `paid`. Данные не потерялись.

**Сценарий 4. Обновляем (меняем) только один сервис.**

```powershell
docker compose up -d --build --no-deps --force-recreate payment-service
```

Пересобирается и перезапускается **только** `payment-service`. Его база, остальные сервисы, их базы, брокер и
шлюз не трогаются. В `docker compose ps` у всех остальных время работы («Up N minutes») продолжает расти.

## 5. Что сказать преподавателю (коротко)

1. «В системе 6 бизнес-микросервисов: auth, user, product, order, payment, notification. У каждого свой
   контейнер и **своя отдельная база данных в отдельном контейнере**. Плюс шлюз и RabbitMQ — это инфраструктура.
   Всего 14 контейнеров».
2. «Сервисы не зависят друг от друга при запуске. Каждый ждёт только свою базу и брокер, поэтому любой можно
   выключить, перезапустить или обновить отдельно».
3. «Если сервис упал, шлюз отвечает понятной ошибкой 502 только на его запросы. Остальные запросы работают».
4. «Если упал процесс, Docker сам перезапускает контейнер (`restart: unless-stopped`). Это я показываю через
   `/chaos/crash` — он имитирует аварию».
5. «Если упала база одного сервиса, страдает только он: отвечает 503 и восстанавливается сам, когда база
   вернётся. Чужие базы не затрагиваются».
6. «Асинхронные события идут через RabbitMQ. Пока сервис лежит, события ждут в очереди, а после подъёма
   обрабатываются. Так заказ, сделанный во время падения оплаты, сам становится оплаченным».
7. «Обновление одного сервиса — `docker compose up -d --build --no-deps <сервис>` — перезапускает только его».

## 6. Возможные вопросы

**Почему контейнеров 14, а не 6?**
Микросервисов 6. У каждого есть ещё своя база данных — это тоже отдельный контейнер, чтобы падение одной
базы не задевало другие сервисы. Шлюз и RabbitMQ по условию задания не считаются бизнес-микросервисами.

**Что если упадёт шлюз?**
Это единая точка входа, без неё клиенты не достучатся до API. Сами сервисы при этом продолжают работать и
обмениваться событиями: заказы оплачиваются, уведомления создаются. В реальной системе шлюз запускают в
нескольких копиях за балансировщиком.

**Что если упадёт RabbitMQ?**
Синхронные запросы продолжают работать: вход, каталог, профили, просмотр заказов. Каждый сервис
переподключается к брокеру автоматически (`connect_robust`). Но события, отправленные именно в момент, когда
брокер лежит, теряются (в логе будет ошибка `event publish failed`). Это известное ограничение, оно указано в
README. В реальной системе его решают паттерном «transactional outbox» и кластером RabbitMQ.

**Где видно, что запросы проходят через несколько сервисов?**
В логах: `docker compose logs -f order-service payment-service`. У всех строк одной операции одинаковый
`request_id`, даже когда она прошла через RabbitMQ.

**Не опасен ли `/chaos/crash`?**
Он включается только переменной `CHAOS_ENABLED=true` (для демонстрации), требует внутренний токен и недоступен
через шлюз. В продакшене его выключают.
